# 坊洁巡维 · 公厕开放时段核算

把巡维停水和故障记录裁剪到公厕承诺开放的时间窗，按设施分钟出具可复核的月报。

## 使用场景

模拟客户为坊洁市政环卫站。桥西、站前、河畔和北坊四个片区共管理 4 座公厕，由 2 组巡维人员轮班。早晚班在纸质交接表记录开闭门和恢复时间，分析员在 Excel 拼接跨夜记录，片区负责人从工作群收图签发月报。原流程容易把跨夜记录切错日期、重复扣减同一设施的多条报障，也容易把整修期间没有开放承诺的设施标成 0% 可用。

上游为开放规则台账和巡维交接记录。工作台负责冻结、裁剪、分钟加权、审阅和发布。下游为街道环卫月报和巡维排班会，按快照编号及 SHA-256 对账。

| 角色 | 演示账号 | 页面和典型操作 |
| --- | --- | --- |
| 分析员 `analyst` | `analyst` | 读日历、停用及全部版本，登记设施、窗口及停用，建版并执行，下载已核算版本 |
| 业务复核 `reviewer` | `reviewer` | 读日历、停用及全部版本，复核并发布已核算版本，下载月报 |
| 观察员 `viewer` | `viewer` | 读日历和停用，通过月报审阅查看及导出已发布版本 |

演示账号统一密码 `Fangjie2026!`。会话使用有效期 8 小时的 JWT，每次 API 请求以数据库里的角色判断权限。登记、建版、提交、核算完成或失败及发布写入审计表。

## 十一月工作剧本

1. **08:30** 分析员林清从 `开放规则_2026-11.xlsx` 核对桥西全天、站前每天 20:00 至次日 02:00、河畔每天 07:00 至 19:00，北坊整修整月无计划。站前另有 21:30 至 23:00 的重叠窗口。
2. **08:45** 打开「停用核对」，对照 `巡维交班_2026-11.csv` 的 8 条初始记录。11 月 12 日站前 23:30 停水，与 11 月 13 日 00:15–03:10 的故障交叠，并延伸到闭馆后。
3. **09:00** 在「窗口核算」新建 `十一月巡检·首次冻结`，月份填 `2026-11`。版本保存了当时的开放规则及会与月份相交的事件。
4. **09:45** 补录河畔的 `WX-1109`，开始 `2026-11-12 09:00`，恢复 `09:40`，原因为设备故障，备注 `入口指示灯故障，现场更换`。
5. **10:00** 新建 `十一月巡检复核`，分别执行两份快照。首次冻结在 75,600 分钟计划内有 285 分钟有效停用，复核版有 325 分钟。复核版实际可用 75,275 分钟，全辖区 99.57%。
6. **10:15** 业务复核陈亭查看「月报审阅」。选择 11 月 1 日，确认站前凌晨只扣 00:00–00:30。切换到 11 月 13 日，确认停用轨道止于 02:00。核对北坊的 `无开放分母` 后发布复核版。
7. **10:30** 观察员周桐打开发布月报并导出 `开放时段-2026-11-V2.csv`。核对 `TOTAL` 行和 SHA-256，北坊的可用率单元格留空。

两个上游文件名用于说明值班剧本，演示样本由 `backend/scripts/seed_demo.py` 写入；本版在工作台逐条登记。

## 指标口径

- 时间按北京时间解析，最小单位为分钟。月份、周规则展开段及停用都是左闭右开区间 `[start, end)`。周规则以开门日归属，最多延续 24 小时。每月从上月最后一天开始展开规则，保留跨入当月午夜后的一段，再裁剪到当月。
- 每座设施分别合并计划窗口为 `P`、合并全部停用原因的区间为 `O`。有效停用为 `|P ∩ O|`，闭馆停用为 `|O| − |P ∩ O|`，实际可用为 `|P| − |P ∩ O|`。事件明细可单独追溯，重叠事件的明细分钟不能直接求和。
- 单设施可用率为 `100 × 实际可用分钟 ÷ 计划开放分钟`。辖区先分别汇总分钟，再做同样的除法。分母为零时，API 为 `null`，界面标注 `无开放分母`，CSV 留空。可用率保留两位小数，按四舍五入显示。
- 快照以 PostgreSQL 的同一读视图采集输入并计算 SHA-256。后台以 `facility-minute-v1` 从冻结数据生成结果，CSV 带版本号、公式版本和输入摘要。Redis 唤醒 worker，PostgreSQL 持久化排队及结果。任务异常回滚后仍可被后台接手，业务计算失败可从页面重试原快照。

## 启动与开发

在独立使用项目时，从项目根目录启动。批次验收需从批次根目录调用共享脚本。

```bash
cp .env.example .env
docker compose up --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

| 入口 | 地址 |
| --- | --- |
| 工作台 | `http://127.0.0.1:18280/` |
| API 和健康检查 | `http://127.0.0.1:19280/docs`、`/health` |
| PostgreSQL | `127.0.0.1:17780` |

前端原生 HTML/CSS/JavaScript 通过 Nginx 提供，`/api/` 代理至 FastAPI。后端和 worker 共用 Python 3.11 镜像。PostgreSQL 16、Redis 7 与 CSV 导出各有其命名卷。修改 `frontend/src` 或 `backend/src` 后，以 `docker compose up -d --build <service>` 重建相关服务。独立开发需停栈时运行 `docker compose down`；本地样本确认可丢弃时，可追加 `-v` 清除数据卷。

| 环境变量 | 用途 |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | Compose 名称，默认 `restroom-availability` |
| `FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT` | 本机回环端口，默认 `18280`、`19280`、`17780` |
| `NETWORK_SUBNET` | 默认 `10.221.211.0/24` |
| `POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD` | 数据库初始化和连接参数 |
| `JWT_SECRET` | 签名密钥，独立部署时使用自有随机值 |
| `SEED_DEMO` | 启动时登记演示数据，使用自然键忽略已有行，默认 `true` |

`backend/migrations` 定义持久化表，`backend/src/services/availability.py` 计算区间，`backend/src/worker.py` 消费待核算版本。`frontend/src/pages` 包含四个业务模块，共用时间轨道、状态标签和编辑对话框。共享枚举 `Role`、`Reason`、`Status` 见 `backend/src/constants/business.py`、`frontend/src/constants/business.js` 和 `backend/migrations/001_initial.sql`。权限在身份依赖、菜单及页面按钮中使用，原因在停用表单及列表中使用，快照状态在服务转换、工作队列及月报视图中使用。

## 使用边界与许可

适用于周重复开放规则以及已有恢复时间的停用事件。临时节假日规则、未恢复事件、批量导入和已发布版本撤回未纳入此版。月度快照按采集时的开放规则回算，录入人员应先核对规则是否适用于所选月份。此仓内容供本批次模拟和验收使用，未另授开源许可。
